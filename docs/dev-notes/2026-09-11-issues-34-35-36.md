**2026-09-11.** Three reports from mirror176 on 2.3.0-rc4. Two were real bugs and are fixed; the
third is a container-format redesign and is not in this release.

## #34 — "rotating restarts transcribing" 🧪 VERIFYING — measured on the OP9 by Claude, awaiting the maintainer

> Corrected 2026-09-11: this heading first said ✅ VERIFIED. A check run by Claude is not the
> maintainer's confirmation, so it is VERIFYING until he reports. **To settle:** rotate the phone during
> a manual transcription; the percentage should keep climbing rather than drop to 1%.

### What was actually happening

**The transcription never restarted.** Measured on the OP9 (Android 14) against a 19.7-minute
recording, with logcat running and the on-screen figure sampled through `uiautomator` every ~2 s:

```
10:53:34 41%   10:53:36 43%   10:53:38 45%   10:53:40 46%   10:53:43 47%   10:53:45 49%
>>> rotate 10:53:47
10:53:47  1%   10:53:49  3%   10:53:52  6%   10:53:54  9%   10:53:56 12%   10:53:58 14%
10:54:00 50%  (and steady from there)
```

Meanwhile the log shows one worker, one PID, passes 1→4 in order, and a normal finish. The run was
untouched; only the number moved. But from the outside a figure that falls to 1% and climbs again is
indistinguishable from work starting over, which is exactly what was reported — and the reporter's
"you can repeat this to reset it multiple times" is the same effect on each rotation.

### The cause

`TranscriptionProgress.display()` predicts a figure between whisper's anchors from **a clock** and
**the last value shown**, because whisper only reports at chunk boundaries and a number that sits
still reads as a hang. Both of those lived in the Home screen's composition
(`SmoothedTranscriptionPercent.kt`: `remember(current) { mutableIntStateOf(0) }` and a
`LaunchedEffect` that took `startedAt` when it began). A rotation destroys the composition, so the
clock restarted at zero, `previous` went back to 0, and the curve was drawn again from the start.
The 13-second climb before it snapped back to 50% is the curve; the snap is whisper's next real
anchor arriving.

### The fix

The figure is now kept by the worker that is doing the transcribing
(`TranscriptionProgressTracker`), which is the arrangement `SummaryWorker` already used — so the two
long-running jobs in this app now report progress the same way. The screen renders what the run
publishes and keeps only the hold-at-100 at the end, which really is about the screen.

Announcing the same recording twice is deliberately a no-op, so nothing outside the run can restart
its clock; a *different* recording resets it, so a batch does not open at the previous figure.

**Verified on the OP9 after the fix** — rotation at 11:07:12 during a run: `50% → 52% → 53% → 54%`,
straight through the rotation and back.

## #35 — "deleting a call during transcribing doesn't end the job" 🧪 VERIFYING — measured on the OP9 by Claude, awaiting the maintainer

> Corrected 2026-09-11 for the same reason as #34. **To settle:** delete a recording while it is being
> transcribed, with another queued behind it; the queued one should start straight away.

Deleting a recording removed its rows through `TranscriptCascade`, but nothing told the engine to
stop. whisper carried on to the end of the file producing a transcript of a recording that no longer
existed — and because the engine serialises every run onto one thread, everything queued behind it
waited for a result that was thrown away. That wait is what the reporter saw as "queued recordings do
not start for a bit".

`TranscriptionInFlight` records which recording the runner is working on. The cascade — the single
choke point every delete goes through — asks it, and aborts the engine when the deleted recording is
the one in flight. The runner already treats an abort as "no result": it removes the row and moves on
to the next recording.

**Verified on the OP9**, deleting 30 s into a four-pass run:

```
11:10:39.758 CV:TranscriptCascade: Stopping the transcription of a recording that has just been deleted
11:10:39.784 CV:TranscriptionRunner: Transcription of …ogg was stopped
11:10:39.792 WM-WorkerWrapper: Worker result SUCCESS
```

34 ms from confirming the delete to the run being over, against the ~90 seconds it would otherwise
have spent finishing.

## #36 — store recordings as Matroska `.mka` ⛔ NOT IN 2.3.0

A thoughtful request: one container holding both sides as separate audio streams, the transcript as a
subtitle track, and caller/date/summary/notes as metadata — so everything is portable and readable by
other software instead of living in CallVault's database, and merging becomes a container operation.

**The blocker is that Android cannot write Matroska.** `MediaMuxer` supports MPEG-4, 3GPP, WEBM, OGG
and HEIF only — checked 2026-09-11 — and none of them is `.mka`. WEBM is a Matroska subset, but the
platform muxer offers no subtitle track and no general metadata. Jetpack Media3's muxer package has
`Mp4Muxer` and `FragmentedMp4Muxer` and nothing else. Reading is not the problem: the platform
demuxes `.mkv` for common codecs.

So shipping this means bundling or writing a Matroska muxer (libmatroska or ffmpeg — a new native
dependency, its size, its licence, its build), and then changing every path that touches a recording:
the three capture paths, playback, merge/un-merge, Drive backup, retention, the catalog, and the
migration for every recording that already exists.

That is a container migration, not a fix, and it would be the largest single change this app has
made. It does not belong in a release that is already at rc and waiting on field verification of a
capture fix. Entered in the backlog with the detail above; worth answering the reporter with the
`MediaMuxer` fact, because it is the thing that decides it.

# Issues #31, #32, #33 — the same reporter, analysed the same day

## #33 — progress stalls at ~73%, then jumps 🧪 VERIFYING

Whisper reports progress only at the top of each 30-second decode window
(`whisper.cpp` main loop, `progress_cur = 100*(seek-seek_start)/(seek_end-seek_start)`), so on most calls
the figure shown is the prediction, not whisper. `TranscriptionProgress` drew that prediction as
`95·(1−e^(−1.6·ratio))`, which is **75% at ratio 1** 📐 (52% at 0.5, 68% at 0.8). The estimate is
calibrated per phone, so runs finished while the bar read ~75% and then snapped to 100 — exactly the
report.

Now linear to **90% at the estimate**, then `90 + 5·(1−e^(−1.5·(ratio−1)))` beyond it (93% at 2×, 94% at
4×, never 95). Whisper's anchors still win when they are ahead. `SummaryWorker` uses the same function,
so summaries change too. **Measured on the OP9 by Claude (rc16), 5-minute recording, estimate 26 s:** `2 12 20 28 36 44 53 61 69 77 → 100`,
sampled every ~2.5 s — steady, no stall. The last reading before the end was 77%; readings lag the run by
about two seconds, and the curve itself stood near 85% at that moment.
**To settle:** watch a manual transcription on a real call; the figure should climb steadily and be well
past three quarters when it finishes.

## #31 — notifications

### 1. The warm-phone notification on a run you started 🧪 VERIFYING

Decided by the maintainer: a manual run already had the confirmation dialog, so it shows no notification;
automatic runs keep it. **One exception added, and why:** the notification is also what makes the job a
foreground service, and the JobScheduler reference says a job that is not one "will still be stopped after
10 minutes if the system is busy" from Android 12, and always was on Android 11 (our minSdk). A stopped
transcription restarts from zero. So a manual run estimated at ≥ 8 minutes keeps the notification
(`TranscriptionNoticePolicy.LONG_RUN_MS`). The worker logs which way each run went.

**Measured on the OP9 by Claude (rc16):** no `heavy_work` notification at any of 24 samples through the run;
the worker logged `No notification: the user just confirmed this run and it is short (~26s)`.
**To settle:** start a short transcription from the app — no "Transcribing a recording" notification.

### 2. "Call in progress — Press to start recording" flashing ✅ VERIFIED 2026-09-11

> Maintainer, on a real call with rc17: the "Press to start recording" notification no longer appears.
> Same call surfaced the next problem — see "Two notifications during a recorded call" below.

Two flashes, both confirmed in code:

- **At the start:** `onStartCommand` posted `currentState` before acting, and a fresh service is
  `Standby(null)` — so every automatic call showed the Record prompt before `Starting`.
- **At the end:** `stopRecordingSessionAndService` set `Standby(null)` (whose setter re-posts the
  notification) before `stopForeground`. A failed start's `finally` could also re-promote a service that
  had already called `stopSelf`.

The opening notice now describes the state the command is entering (`RecordingNoticePolicy`), and an
`isShuttingDown` guard stops re-posting once the stop path has begun; the next command clears it.

**Not changed, a finding:** when a One UI VoIP call raises OFFHOOK, the carrier start is ignored but the
service stays foreground in Standby for the whole call, showing the Record prompt. Stopping the service
there would make the end-of-call STOP (sent with `startService`) create a fresh instance that must
`startForeground` from the background, which Android 12+ can refuse — so it needs its own design.

**To settle:** make or take a normal call with auto-record on and watch the shade as it starts and ends.

### 3. "Ready to record calls" always showing — ❌ first attempt rejected 2026-09-11

rc17 added *Settings ▸ General ▸ Visual settings ▸ Status notification*, which opened Android's own switch
for the channel. **The maintainer rejected it:** he does not want users sent to system notification
settings; he wants the notification itself toggleable **inside CallVault**. Reverted in `d7b7a40`.

**An in-app toggle cannot hide it while the recorder stays warm.** Checked in AOSP main
`NotificationManagerService` (2026-09-11): a foreground-service notification posted on a channel whose
importance is MIN or NONE is raised to LOW — "Increase the importance of fgs/uij notifications unless the user
had an opinion otherwise". Only the *user's* own channel choice survives that, which is exactly the
system-settings route the maintainer rejected.

And the service behind it is not only the warm recorder. `DaemonKeepAliveService` is the **only** place VoIP
calls are detected (`VoipCallDetector`), and it runs the Wireless-debugging ownership observer (#30), the USB
and Developer-options observers, the daemon-death watchdog and the USB data-mode warning. A switch that stopped
it would silently stop all of those.

**Decision, 2026-09-11:** left as it is — no toggle. The maintainer's rule: only if very simple and low risk.

### 4. Two notifications during a recorded call — found 2026-09-11

Maintainer, same call: the shade showed **"recording in progress"** and **"Ready to record calls"** at once.
The second is moot while a call is being recorded. The keep-alive notification already switches to a
recording title for VoIP calls (its `voipRecording` branch), but a carrier call is recorded by
`RecordingForegroundService` under its own notification id, so the keep-alive keeps saying "Ready".

Android supports one app's foreground services **sharing a notification id**: `ActiveServices
.cancelForegroundNotificationLocked` skips the cancel while another foreground service in the package still
holds that id (checked in AOSP main, 2026-09-11). That makes "one notification that says Ready when idle and
shows the recording while a call is recorded" a supported arrangement rather than a hack.

**Implemented the same day — ✅ VERIFIED 2026-09-11** (maintainer, real recorded call on the OP12 with rc19: one
notification throughout, "Ready to record calls" back after hang-up — "it worked perfectly"). Briefly backlogged as not "very simple and low risk"; the maintainer
then asked for it fixed now. `SharedStatusNotice` holds the arrangement:

- `RecordingForegroundService` posts under the keep-alive's id (4720) and **claims** it before each post; it
  **releases** it after each `stopForeground`. A start ignored because the VoIP recorder has the call keeps its
  own id, so the keep-alive's VoIP recording notice is never hidden.
- `DaemonKeepAliveService` and the post-boot `CallMonitorService` skip every re-post while a call holds the id, and
  if they have to `startForeground` meanwhile they post the recording's notification, not "Ready".
- On release the keep-alive re-posts "Ready", because Android leaves a shared id's notification up.

**To settle:** make a recorded call. The shade should show **one** notification from the moment it starts until
hang-up, and "Ready to record calls" should come back after it. Worth one call on a freshly rebooted phone too,
where the post-boot monitor holds the same id.
