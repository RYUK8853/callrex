# Issue #24 — Wireless debugging switched off, USB debugging "turning itself on", Shizuku stealth mode

**2026-09-11.** Reporter **fcthemaster** — a different person from mirror176 (see `never-assume-ask`). OnePlus 12
(CPH2581), Android 16, Italian locale, **CallVault 2.2.0**, standalone mode, VoIP recording on, resilient recording off.
Debug and system reports generated **2026-09-11 10:09** on 2.2.0, plus three screenshots from the same session. He uses
thedjchi's Shizuku fork with **stealth mode**.

All three complaints are either fixed in 2.3.0 or not CallVault's doing. 🧪 None is confirmed by him yet.

## 1. "CallVault keeps disabling Wireless debugging" — the #30 bug, fixed in 2.3.0

The 2.2.0 log says it outright, repeatedly:

```
10:06:43.627 CV:DaemonKeepAlive: Wireless debugging switched on by hand but USB debugging covers adbd — switching it back off
10:07:48.263 CV:DaemonKeepAlive: Wireless debugging switched on by hand but USB debugging covers adbd — switching it back off
```

That is exactly what issue #30 reported. 2.3.0 only switches off Wireless debugging that CallVault itself turned on;
a change made by anyone else clears the ownership and the switch is left alone (`only-undo-switches-we-set`,
✅ verified on the OP12 2026-09-07).

## 2. "Shizuku in stealth mode is not recognised" — the package-name bug, fixed in 2.3.0

- His Shizuku is running ("Shizuku è in esecuzione, Versione 13.6, adb") and lists **CallVault as authorised**.
- CallVault's Settings says **"Shizuku non è installato"** — not installed.
- The system report shows adbd starting it from `…/moe.shizuku.privileged.api.tqzm2-…/lib/arm64/libshizuku.so`:
  stealth mode renamed the package to **`moe.shizuku.privileged.api.tqzm2`**.

2.2.0 looked Shizuku up by its fixed package name, so a renamed one reads as absent. 2.3.0 asks the binder first and
finds the manager by the permission it declares (`shizuku-detection-not-by-package-name`, proven on the OP9 against a
real stealth clone). This is very likely the original "hide mode" report that fix came from.

## 3. "USB debugging re-enables itself" — his Shizuku fork, not CallVault

- **CallVault never turns USB debugging on by itself.** The only write to `adb_enabled` in the app is the Settings
  switch, driven by a tap (`SettingsScreen.UsbDebuggingToggle`) — checked at `v2.2.0` and at HEAD. Its
  "adbd has no transport; restoring" step re-enables **Wireless** debugging, not USB.
- **thedjchi's fork does turn it on.** Its README lists `WRITE_SECURE_SETTINGS` as "used to toggle USB and wireless
  debugging in the background when starting/stopping Shizuku", and it runs a watchdog that restarts Shizuku.
- **The timeline matches the fork**, not CallVault:

```
10:08:15.869 CV:DaemonKeepAlive: USB debugging switched off and Wireless debugging is off — adbd has no transport; restoring
10:08:21.794 CV:DaemonKeepAlive: USB debugging switched on — Wireless debugging is no longer needed     ← USB turned on by someone else
10:08:22.000 adbd: adbd service requested 'shell:…/moe.shizuku.privileged.api.tqzm2-…/libshizuku.so …'  ← Shizuku (re)started
10:08:23.304 CV:RecorderLauncher: Wireless debugging disabled (DROP_USB_KEEPS_ADBD; commands flow over binder)
```

📐 Inferred from the log and the fork's documentation, not reproduced. On 2.2.0 the two apps fought: the fork switched
debugging on to keep Shizuku alive, and CallVault switched Wireless debugging back off. The 10:01 launch failure
("ensureServerRunning gave up after 3 attempts; connected=false") sits in the middle of that churn. 2.3.0 removes
CallVault's half of the fight, because the fork's change is not CallVault's to undo.

## What would settle it

He installs 2.3.0 with stealth mode still on, and checks that:

1. the Shizuku mode switch in CallVault is no longer greyed out as "not installed";
2. Wireless debugging he (or the fork) turns on stays on;
3. if USB debugging still turns on, it happens when Shizuku starts or restarts — the fork's watchdog.

A 2.3.0 debug report would show the `Shizuku manager:` line in the configuration header, which names the renamed package.
